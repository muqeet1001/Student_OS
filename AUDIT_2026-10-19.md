## 3. Errors

### Routing and navigation

**R1 — The admin mobile bar silently drops two of five destinations.** `medium`
`client/src/components/MobileRouteNav.jsx:10`

```js
? adminLinks.filter((link) => ['/admin/overview', '/admin/students', '/admin/drives', '/admin/tasks', '/admin/outcomes'].includes(link.path))
```

`adminLinks` (`client/src/routes/pageRegistry.js:13-24`) contains no `/admin/tasks`
and no `/admin/outcomes` — those were renamed to `/admin/actions` and
`/admin/reports`. The filter therefore matches three entries, not five, so Action
Centre and Reports are unreachable from the mobile bottom bar. Nothing warns: the
component renders a valid three-item nav.

Fix: filter on `/admin/actions` and `/admin/reports`.

*Checked and clean:* no client path/verb points at a handler that does not exist
(94 call sites vs 180 handlers). The four apparent mismatches — `/problems/:slug/:mode`,
`/profile/me/:section[/:id]` — are dynamic segments resolved at runtime by
`section ∈ {skills, projects, certifications, education, experience}` and
`mode ∈ {run, submit}`, both of which the server registers. No router shadows a
literal sibling with an earlier `:param` route.

### Logical

**L1 — The login handler's timing-safety comment describes code that is not there.** `medium` (security-adjacent)
`server/src/controllers/auth.controller.js:132-135`

```js
// Compare regardless of whether the user exists so timing does not reveal
// which emails are registered.
const matches = user ? await user.comparePassword(password) : false;
```

When the address is unknown the bcrypt comparison is skipped entirely, so the
response returns in a few milliseconds instead of ~100 ms at cost 12. The comment
states the opposite of the behaviour, and the endpoint is rate-limited to 20
attempts per 15 minutes per IP — enough to time-test a shortlist.

Fix: always run one comparison, against a fixed dummy hash when `user` is null:

```js
const DUMMY = '$2a$12$....................................................';
const matches = await bcrypt.compare(password, user?.password ?? DUMMY);
if (!user || !matches) throw ApiError.unauthorized('Incorrect email or password');
```
(`user.password` is already selected via `.select('+password')`.)

**L2 — "Sign out other devices" signs out the current device too when the refresh cookie is missing.** `medium`
`server/src/controllers/auth.controller.js:242-257`

```js
const presented = req.cookies?.[REFRESH_COOKIE] ? hashToken(...) : null;
const before = user.refreshTokens.length;
user.refreshTokens = user.refreshTokens.filter((entry) => entry.tokenHash === presented);
```

With `presented === null`, the filter keeps nothing: every refresh token, including
the caller's, is deleted. The response still says `revoked: before` and
`'Other sessions signed out.'`, and the access token keeps working until it
expires — so the user is told one thing and gets another on the next refresh.
Reachable from any client that authenticates with a Bearer token and no cookie
(a mobile shell, a script), and from a browser whose cookie was blocked.

Fix: require the cookie for this endpoint (`400` if absent), or only count
`before - after` and word the response as "all sessions" when `presented` is null.

**L3 — "Solve 3 DSA problems" is marked complete after one submission.** `low-medium`
`server/src/services/todayPlan.js:34-45`

```js
const solvedToday = coding.streak?.lastSolvedAt
  ? new Date(coding.streak.lastSolvedAt).toDateString() === new Date().toDateString()
  : false;
...
label: 'Solve 3 DSA problems',
done: solvedToday,
```

`done` is derived from "has any accepted submission today", while the label asks for
three. The dashboard's `plan.completed / plan.total` therefore reaches 1/4 on the
first solved problem, and the task disappears from the "what should I do next" list
while two thirds of it are undone.

Fix: compare today's accepted count to the target (the value is already aggregated in
`computeStreak`'s input path), or relabel to "Solve a problem today" so the completion
signal matches the ask.

**L4 — Every duplicate-key error is reported as an account conflict.** `low` (message accuracy)
`server/src/middleware/error.js:39-41`

```js
} else if (error?.code === 11000) {
  const field = Object.keys(error.keyPattern || { field: 1 })[0];
  error = ApiError.conflict(`An account with that ${field} already exists`);
}
```

This handler serves every model. A duplicate company `slug`, drive title or
`OneTimeToken.tokenHash` surfaces to the user as *"An account with that slug already
exists"* — wrong entity, and it leaks index internals in the wording.

Fix: neutral phrasing (`A record with that ${field} already exists`) or map known
collections to nouns.

**L5 — `useApiResource({ enabled: false })` leaves `loading` true forever.** `low` (latent)
`client/src/hooks/useApiResource.js:14,19`

```js
const [loading, setLoading] = useState(enabled);
...
if (!enabled) return undefined;   // never clears loading
```

A disabled resource reports `loading: true` for the life of the component, so the
usual `if (loading) return <LoadingBlock />` guard pins a spinner on screen. It is
invisible today only because both call sites happen to guard themselves first.

The same flag also makes `client/src/pages/ResumeBuilder.jsx:21` self-contradictory:

```js
useApiResource(targetJobId ? `/jobs/${targetJobId}` : '/jobs/top-matches',
              { enabled: Boolean(targetJobId) })
```

The fallback path `/jobs/top-matches` can only be chosen when `targetJobId` is
falsy — which is exactly when `enabled` is false. That branch is unreachable, so
"top matches" is never fetched and the suggested version title always falls back to
`Resume N`.

Fix: `useState(Boolean(enabled))` and `setLoading(false)` on the early return; then
decide whether ResumeBuilder wants the fallback at all.

**L6 — Integration suites skip silently, and the summary reports zero skips.** `high` (for confidence in the suite)
`server/tests/helpers/integrationHarness.js:44-45`, all 12 `*.integration.test.js` files

Running one suite in isolation:

```
⚠  INTEGRATION TESTS SKIPPED (pwreset) — MONGO_URI is not set in server/.env
# tests 0
# suites 1
# pass 0
# fail 0
# skipped 0
```

The suite is registered with `describe(name, { skip })`, and node counts the skip at
the suite level — which its summary counters do not include. `# skipped 0` is
therefore printed for a run that executed none of the integration assertions, and the
599 − 417 = 182 gap against the figure in `OUTSTANDING_TASKS.md` is the size of what
went missing. The harness has no in-memory fallback: `startHarness` reads
`config.mongoUri` and gives up when it is empty.

Consequences: a local `npm test` looks fully green while every route/role/populate
assertion is absent, and `OUTSTANDING_TASKS.md`'s "0 skipped" is not evidence that
they ran. The same doc states the integration suite "was run against an in-memory
MongoDB" — nothing in the harness starts one, so that claim needs either a pasted
`MONGO_URI` or retracting.

Fix (cheapest): when `skipReason` is set, register a failing test instead of a
skipped suite in CI, or set `process.exitCode = 1` under `process.env.CI`. Also print
`SUITE SKIPPED` to stdout rather than `console.warn`, so it survives a piped run.

### Display

**D1 — The confirmation page can never show the address it confirmed.** `medium`
`client/src/pages/VerifyEmail.jsx:37`

```js
setAddress(data.email ?? '');
```

`POST /auth/verify-email` returns `{ user, emailVerifiedAt, message }`
(`server/src/controllers/auth.controller.js:459-466`) — there is no `email` field.
`address` stays `''`, so the "Password recovery will use {address}." block at
lines 100-104 never renders. The sibling page gets this right:
`ForgotPassword.jsx:45` reads `sent.email.available`, because
`/auth/password/forgot` returns `mailerStatus()` in `email`. Here the same key name
would have been an object, not an address.

Fix: `setAddress(data.user?.email ?? '')`.

**D2 — The configured placement season name is never displayed.** `low`
`client/src/context/AdminScopeContext.jsx:28`

`seasonName` is derived from `institution.placementSeasonName` (falling back to
`Class of {year}`) and exposed on the context, but no consumer reads it — grep finds
it only at its definition. `AdminDashboard.jsx:55` hard-codes `Class of {year}` in the
season picker instead, so an institution that names its season sees the name
everywhere except the one screen that switches between seasons.

Fix: use `scope.seasonName` for the picker's label, or delete the field.

**D3 — Deployment documentation points at a directory nothing writes to.** `low` (doc/behaviour mismatch)
`README.md:285-288`, `OUTSTANDING_TASKS.md` A4

README: *"Uploaded avatars and certificates are written to `server/uploads`; mount a
persistent volume there."* The code disagrees: `middleware/upload.js` uses
`multer.memoryStorage()` and never touches disk, and `profile.controller.js:69-91`
persists avatars through `services/fileStore.js`, which is GridFS
(`BUCKET`-based `GridFSBucket`). Certificates take the same path. The only remaining
references to `uploads/` are `config.uploadsDir`, a `mkdirSync` at
`server/src/index.js:8`, and a `/uploads` skip in the SPA fallback — dead code.

The consequence is a deployment instruction that costs a volume nobody needs, and a
backlog item (A4) justified by a premise that is no longer true.

Fix: delete the uploads paragraph from README, drop `uploadsDir`/`mkdirSync`,
and restate A4.
